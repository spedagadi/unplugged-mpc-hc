## 2. What the app is, in one paragraph

`C:\code\unplugged-mpc-hc\tools\native_ui\native_ui.cpp` (single translation unit, ~7,400 lines)
is a Win32/MFC shell: one borderless fullscreen `CFrameWnd`, a child `UnpluggedVideoHost` window
that MPCVR parents its own drawing window (`VRWindow`) into, and four chrome panes (top strip,
status rail, settings rail, transport bar) plus transient top-level cards. Video decoding and
grading are in `src\mpchc_engine` (via `s3engine.dll`), rendering in
`c:\code\unplugged-VideoRenderer` (`unplugged_vr.ax`).

Worth knowing before touching it: MPCVR **creates its window AFTER the panes exist**, so it
lands above them in z-order; the taskbar is a topmost appbar the shell will not auto-hide for a
borderless popup; and any call into the renderer while a DeckLink capture is streaming can block
on the renderer lock held by the capture thread.

## 4. THE UNSOLVED DEFECT

### 4.1 Symptom, as reported and as reproduced

The operator: "single click on the video window fucks the system"; "panels become unresponsive
after I click the video and then the rail". The app keeps playing, keeps painting, keeps its
300 ms timer, and takes no input - mouse or keyboard - until the operator leaves and returns.

### 4.2 Measurements (all from `bin\app\Release\native_ui_log.txt` and OS-level hooks)

Instrumentation used (all since removed from the tree): a `WH_KEYBOARD_LL` tap, a `WH_MOUSE_LL`
tap, a `WH_GETMESSAGE` tap, a peeking queue probe, `WindowFromPoint`/`GetGUIThreadInfo` state
lines once a second, and a subclass probe on `VRWindow`.

| Time | Measurement | Conclusion |
|---|---|---|
| 13:03:00 | `[kb] down vk=4E ... fg=our frame focus=our frame` then **no** `[CLICK] key` for 3 s | keys are real, addressed at our focused window, and do not reach a window procedure |
| 13:03:00 | `[state] ... topmost=1 active=1 capture=none` during the same seconds | app was foreground and healthy while input was missing |
| 13:08:54 | `[queue] stuck msg=0x0100 target=frame vk=4E` repeated every second | the key sits in **our thread's** queue |
| 13:16:38 | `[pump] retrieved msg=0x0100 ... x4, 0x0101 x4, 0x5B` in one 1 ms burst | retrieval happens only when the operator switches away |
| 13:29:11-14 | `[mouse] down at (...) under=<our window> ours=1 capture(thread)=0` x10, **no** `[CLICK]` | the OS generates real clicks aimed at our windows; they never arrive |
| 13:31:12 | no `[focus]` line, no `[mode]` line, `active=1 topmost=1` | focus is valid; thread is not in menu/move-size mode |
| 13:41:34-38 | clicks land on `VRWindow` (`under=0x140A40`) | a click on the video surface is the trigger |
| 13:46:44 | `[modal]` silent; `GetLastActivePopup == frame` | no modal dialog owns the input |

### 4.3 Mechanisms tested and EXCLUDED

1. `WS_EX_NOACTIVATE` swallowing the first press - fixed earlier, unrelated to this.
2. Mouse capture - `capture(thread)=none` throughout; also checked at OS level.
3. Focus lost / NULL focus - a focus guard (restore when foreground and focus null/foreign)
   never fired once.
4. Modal dialog / popup - `GetLastActivePopup` stayed equal to the frame.
5. `GUI_INMENUMODE` / `GUI_INMOVESIZE` - thread flags were zero.
6. `AttachThreadInput` by any binary in the process - no occurrence in `native_ui.cpp`,
   `mpcchc_engine`, `LAVFilters`, or `VideoRenderer`.
7. A blocked message pump - `[stall]` never fired during the dead periods; the 300 ms timer
   kept printing state lines from inside the pump.
8. Keyboard hardware / "ghost Win key" - real presses, but they were the operator's own escape
   keystrokes, not the cause. This hypothesis cost about an hour and was wrong.
9. Taskbar covering controls - real, fixed, but not this defect.
10. Renderer window above the panes - real, mitigated by re-raising panes each tick, but not
    this defect.

### 4.4 What is left

The evidence is contradictory under documented Windows behaviour: posted messages are dispatched
while input messages for the same thread are not, and `PeekMessage(PM_NOREMOVE)` can see the
pending input. Two candidates remain and both are cheap to test in isolation:

- **A. The composition.** Something about having a DirectX child window inside our host, clicked
   by the user, puts the thread's input into a state Windows does not service. The trigger being
   a click on `VRWindow` supports this.
- **B. The environment.** A third-party component (a hook DLL, security software, a display or
   input driver) interferes with input delivery for this process when the video surface is
   clicked. The machine has a Logitech G513 with Logitech services running and an HDMI capture
   path; none of that was implicated by measurement, but it was not ruled out either.

### 4.5 The experiment that should settle it (do this first)

`tools\input_proof\proof_host.exe` already exists in this repo: a minimal host with the same
topology (frame + video host + one pane). Run it, click the video area, then click the pane.

- If input dies there too, it is **A** and the fault is in our composition - bisect from that
  harness (it has no engine, no chrome, no timers).
- If it does not, it is **B**, and the same harness with the engine attached, then with the
  renderer, bisects the process.

Do not add instrumentation back into the shipping shell to chase this. Two global low-level
hooks were installed for this investigation; they write a log line from inside the input path
and were themselves a suspect for a while. The shell must not carry them.

## 8. Design contract - status

**The contract is [`tools\native_ui\UI-CONTRACT.md`](UI-CONTRACT.md).** It was drafted and
reviewed with the operator on 2026-10-30 and is the governing document for the rebuild. It is
not optional background: the rebuild is judged against it, and section 9 of the contract ("no
change without an invariant") is the rule that replaced the patch-on-patch approach.

What it fixes, in short:

- **Layout requirements L1-L5.** The window is divided into non-overlapping bands (one per
  visible pane) with the picture rect as the remainder; the chrome is never over the picture;
  the picture keeps its shape (aspect, crop and NLS warp) across chrome changes; no control is
  laid out where the shell can cover it; `Layout()` is the only code that positions windows.
- **Interaction requirements I1-I7.** The chrome is static - no auto-hide, no reveal gesture,
  no "is the chrome up" state; panel visibility changes only by explicit user action or the
  library screen; every control that is drawn does something; global keys work regardless of
  focus; the cursor is the system's; panes talk to the frame only by posting `WM_APP+n`.
- **Real-time requirements R1-R4.** The UI thread never calls into the renderer; the picture
  rect may change at any moment, including during a live capture, without blocking; no chrome
  operation may resize a swap chain; a freeze is a release blocker.
- **Invariants V1-V6**, each paired with the failure it makes impossible (the measured
  failures are tabulated in the contract's appendix): one rectangle per owner, chrome static,
  one top-level window, no UI-thread renderer call, taskbar band excluded, picture rect
  computed from the bands and never from the window.
- **Component audit.** Keep: `CUiWnd`, the drawing helpers, the four pane classes, the cards,
  the settings/preset/library store, the engine bridge. Replace: `CMainFrame`'s chrome section.
  Delete: the timers, the sampler, `EdgeCheck`, `InBottomDock`, the `SetUi`/`ApplyChrome`
  state, the cursor machinery and the `videorect`/refit path (the last is replaced by the
  deferred rect). Deferred: splitting the single translation unit.
- **Acceptance tests A1-A8** in the contract are the objective release gate.

**What of the contract is already implemented and verified today:**

- Section 5, the renderer's deferred destination rect - implemented in
  `VideoRenderer.cpp` (`SetDestinationPosition` stores, `DoRenderSample` applies) and verified
  live: rail toggles during capture produce `[GEOM] refit ...` in the engine log and
  `applied ...` in `%TEMP%\mpcvr_destrect.log`, with the app responsive throughout.
- V5 (taskbar band excluded) - `TaskbarReserve()` in `Layout()`.
- V3 (one top-level window) - the overlay window is gone; panes are children of the frame.
- V6 (picture rect from the bands) - `Layout()` computes `vid` and sends it as `videorect`; the
  engine keeps the canvas full-window and scales the finished picture uniformly into `vid`.
- I4 for the confirm card - `WS_EX_NOACTIVATE` removed, verified by the VP -> media switch.

**What of the contract is NOT in the current tree** (lost to the restore, re-implement from the
contract): I1/I2 - the static chrome (`ApplyChrome` replacing `SetUi`, no idle timer, no reveal
gesture, no pointer sampler). Until that is re-done, the restored file still contains the old
timer/gesture machinery the contract deletes.

## 9. Product decisions still open

1. **VP transport bar contents.** It draws play/seek/volume/mute, which are disabled in capture
   mode by design (the operator's own earlier rule). Operator feedback: dead-looking controls
   are unacceptable. Proposal on the table: draw only Restart, VideoProcessor, Media Player,
   NLS in VP. Not approved, not implemented.
2. **Rails in VP.** With the picture rect driven by the chrome, toggling a rail during capture is
   now safe (the deferral), but whether rails should re-flow the picture live is unresolved.
3. **NLS kernel.** Shader currently samples bilinear (explicit 4-tap). A Catmull-Rom kernel was
   offered and deferred by the operator.
4. **Dolby Vision P5** plumbing - parked, needs a P5 test clip.
